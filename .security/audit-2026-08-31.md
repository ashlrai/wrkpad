## Executive summary

The expanded candidate remains low risk within its observe-only hardware boundary. No open critical, high, medium, or low vulnerabilities were identified. This audit remediated hook-configuration ownership/CAS issues, state transaction defects, IPv6 authorization, terminal cleanup, and service startup ambiguity before user-level activation.

**Risk rating:** Low
**Open findings:** 0 critical, 0 high, 0 medium, 0 low, 3 informational

## Scope and attack surface

- Authenticated loopback HASP routes for status, events, and local slot recovery.
- Untrusted Claude Code and Codex hook JSON, including parallel subagent identities.
- Executable user hook configuration under `~/.codex` and `~/.claude`.
- Opt-in per-user macOS LaunchAgent configuration and fixed `/bin/launchctl` calls.
- Private token, persisted status state, hook/service backups, and stderr log.
- Read-only USB/HID/process/tool diagnostics and disabled hardware write path.

## Remediated during this audit

### HIGH — Hook repair/uninstall ownership was too broad

Substring matching could have claimed a similar unrelated command. Managed commands now carry an exact `--managed-by dev.wrkpad.hook-v1` grammar; unmarked near matches are preserved by tested repair/uninstall behavior. Exactness also requires only the three canonical handler fields, so an added behavior-changing field such as `async` requires repair.

### HIGH — Hook plan did not bind the exact proposed document

The confirmation ID now includes the full proposed-document hash, source hash, action, target, and canonical command. Duplicate handlers cannot mask a missing event, repair cannot install from an empty target, and stale plans are refused.

### HIGH — Project hook writes could follow redirected paths

Target, dangling, and immediate parent symlinks are refused, non-regular and oversized files are rejected, project scope resolves to the enclosing Git root, and replacements use private same-directory temporary files plus final source comparison.

### MEDIUM — Failed state persistence changed live memory

The server now clones and rolls the reducer back when disk persistence fails. A regression test proves the revision remains unchanged.

### MEDIUM — IPv6 loopback Host validation was malformed

Allowed hosts now use bracketed `SocketAddr` formatting, with a regression test for `[::1]:43187`.

### MEDIUM — Terminal state could survive an error path

The TUI now owns raw mode, alternate screen, and cursor recovery in a drop guard, including partial startup failures.

### MEDIUM — Background service could race an unmanaged listener or binary replacement

Service plans bind the installed executable SHA-256, and ownership requires the exact current executable path rather than any absolute program. Install/start/repair refuse an authenticated listener not owned by the loaded job, use fixed direct argv with no shell or secret environment, and verify authenticated HASP after `launchctl kickstart -kp`.

## Informational items

1. Codex hook trust remains `untrusted_or_unknown` until the operator reviews the exact installed source and command in `/hooks`. Manual adapter ingestion does not prove provider invocation.
2. The wrkpad mutation lock files are fail-closed. A process killed between lock creation and cleanup can require operator inspection and removal of the stale lock.
3. Hardware transport remains read-only. Live USB and HID probes passed but found no board; descriptor, firmware, ownership, lighting, release, reconnect, and soak acceptance remain unavailable.

## Remaining release gates

2. Keep signed/notarized/public artifact claims separate; only a local stable binary is installed today.
3. Before any future HID write, run a new transport-focused audit with exact device tuple, lease, rate limit, readback, signal cleanup, reconnect, and soak evidence.
