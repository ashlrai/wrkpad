## Executive summary

The local-first candidate has a low residual security risk for its current observe-only scope. No open critical, high, medium, or low vulnerabilities were identified after remediation. The audit closed one high-risk token-exfiltration path and four defense-in-depth issues before the audited commit. Physical HID writes remain absent, so hardware write safety is deliberately outside the current executable capability.

**Risk rating:** Low  
**Open findings:** 0 critical, 0 high, 0 medium, 0 low, 2 informational  
**Remediated during audit:** 1 high, 4 medium

## Scope and attack surface

- One native binary; no database, cookies, cloud service, OAuth, web UI, or public listener.
- HTTP routes: unauthenticated `GET /v1/health`; authenticated `GET /v1/state`; authenticated `POST /v1/events`.
- Untrusted inputs: provider hook JSON, CLI flags and environment, local HTTP headers/body, HID descriptors, persisted JSON.
- Sensitive material: a per-user bearer token, raw provider session IDs and working directories before HMAC privatization, and six persisted status slots.
- Consequential capabilities: none. The source has no HID write transport, approval response, command execution, process termination, deployment, or provider-control endpoint.

## Remediated during this audit

### HIGH — External endpoint could receive the bearer token

**Previous impact:** A malicious or accidental `WRKPAD_ENDPOINT` could direct the hook client to an external host, disclosing the local bearer token and sanitized event metadata.

**Resolution:** Client construction now accepts only plain HTTP on `localhost`, `127.0.0.0/8`, or `::1`, with no user information, path, query, or fragment. Rejecting tests cover external, private-network, and proxy-path URLs (`src/client.rs:58`).

### MEDIUM — Token and state reads could follow symlinks

**Previous impact:** A same-user attacker could redirect reads to another file, or exploit operator confusion around persisted state.

**Resolution:** Token and JSON state operations refuse symlinked targets; new files use `create_new`, mode `0600` on Unix, file synchronization, atomic rename, and parent-directory synchronization (`src/config.rs:56`, `src/storage.rs:29`).

### MEDIUM — Provider text could inject terminal controls or retain sensitive titles

**Previous impact:** An untrusted provider title or path component could alter terminal rendering, and provider-supplied session titles could contain customer-sensitive text.

**Resolution:** Adapters ignore provider session titles, retain only a sanitized workspace basename, strip controls from transient working directories, and the engine rejects control characters at its trust boundary (`src/hooks.rs:59`, `src/engine.rs:152`).

### MEDIUM — Idempotency/session state could grow without a bound

**Previous impact:** An authenticated local client could consume memory and persisted disk space with unique event/session identifiers.

**Resolution:** The engine retains at most 4,096 idempotency identifiers, removes evicted session records, caps visible sessions at six, and does not retain unassigned off-only sessions (`src/engine.rs:99`, `src/engine.rs:185`).

### MEDIUM — Mutable CI actions and immediate dependency proposals

**Previous impact:** Retagged third-party Actions or a newly published malicious dependency version could enter CI with insufficient observation time.

**Resolution:** Every Action is pinned to a verified full SHA, workflow permissions are read-only, and Dependabot cooldowns are seven days (`.github/workflows/ci.yml:8`, `.github/dependabot.yml:7`).

## Informational items

### INFO-01 — Hosted dependency advisory result does not yet exist

The local machine does not have `cargo-audit` or `cargo-deny`, and this audit did not silently install tools. CI is configured to install and run `cargo-audit`, but no hosted result can exist until a remote is created and the workflow runs. Treat the first green advisory job as a publication gate, not as already-passed evidence.

### INFO-02 — Hardware security remains deliberately unaccepted

Live doctor output found no recognized board and found ChatGPT Desktop, Work Louder Input, and Logitech software running. `hid_writes_enabled` is false, the lighting frame reports `hardware_applied: false`, and takeover fails closed. Exact descriptor, firmware, exclusive ownership, visible calibration, release, reconnect, and soak evidence are still required before a future writable transport can be reviewed.

## Prioritized recommendations

### Immediate publication gates

1. Create the public remote only after explicit operator authorization.
2. Require the pinned CI matrix and `cargo audit` job to pass on the exact publication commit.
3. Publish an immutable source tag and checksummed binary; do not call it signed/notarized unless those receipts exist.

### Short term

1. Add fixture-based cross-platform tests for macOS, Linux, and Windows device enumeration in hosted CI.
2. Add an SBOM and license/advisory result to release artifacts.
3. Review fixed external executable lookup in doctor before supporting privileged or managed-machine deployments.

### Before any HID write milestone

1. Audit the exact report framing and firmware capability tuple on the physical board.
2. Add an exclusive writer lease, write rate limits, readback verification, release-on-signal/panic/crash, and reconnect/soak tests.
3. Run a second security audit focused on native HID transport, firmware downgrade resistance, and recovery.
